# 🏥 ICU Telemetry Simulator — Jeevan Setu (जीवन सेतु)

> **Simulated Multi-Parameter Patient Monitoring & System Load Testing Engine**

---

## 📌 1. Purpose & Overview

The **ICU Telemetry Simulator** is an integrated developer and demonstration tool built natively into the Jeevan Setu platform. It acts as a simulated medical bedside monitor transmitting 4-parameter physiological telemetry to the existing backend for real-time Early Warning Score (EWS) computation, clinical recommendation generation, and emergency alerting.

> **DISCLAIMER:**  
> *"This module simulates ICU telemetry for development and demonstration purposes. It is not connected to a real medical device and must not be used for clinical care."*

## 🔒 3. Authorization & RBAC

- **Access Level**: **Administrator / Developer** privileges only (`role: 'admin'`).
- **Enforcement**:
  - Direct browser visits require an authenticated admin session (Flask-Login) or valid Bearer JWT.
  - Unauthenticated requests receive **HTTP 401 Unauthorized**.
  - Requests from non-admin accounts (Doctors, Nurses, Attendants) receive **HTTP 403 Forbidden**.
  - All transmitted vitals and diagnostics pass through `@permission_required` and audit logging.

---

## 🩺 4. Simulated Vital Parameters

The simulator generates **ONLY** the 4 core clinical parameters of Jeevan Setu:
1. **Heart Rate (HR)** — *bpm* (Clinical range: 20–300)
2. **Respiratory Rate (RR)** — */min* (Clinical range: 4–80)
3. **Systolic Blood Pressure (SBP)** — *mmHg* (Clinical range: 40–300)
4. **Body Temperature (Temp)** — *°C* (Clinical range: 25.0–45.0)

---

## ⚖️ 5. Architectural Separation: What the Simulator DOES NOT Calculate

| Responsibility | Handled By |
|---|---|
| Vital Generation | **Telemetry Simulator** |
| Parameter Sanitization & Range Validation | **Existing Backend API** (`routes/vitals_routes.py`) |
| Early Warning Score (EWS) Scoring | **Existing EWS Scoring Engine** (`modules/scoring_engine.py`) |
| Transfer Recommendations (ICU ↔ HDU) | **Existing Decision Engine** (`modules/decision_engine.py`) |
| Emergency Critical Alerts | **Existing Alert Engine** (`modules/alert_engine.py`) |
| Transactional Persistence | **Existing MySQL Database** (`vitals`, `ews_scores`, `recommendations`) |
| Clinical Transfer Approval | **Attending Doctor Only** (Never approved by simulator) |

The simulator **NEVER** computes EWS, never determines clinical risk levels, and never approves patient transfers. It acts strictly as an external data telemetry source.

## 🔄 6. Simulation Scenarios

1. **`STABLE`**: Normal adult resting vitals with subtle physiological drift (HR: 70–80 bpm, RR: 14–18 /min, SBP: 116–124 mmHg, Temp: 36.6–37.0 °C).
2. **`GRADUAL_DETERIORATION`**: Progressive 4-phase clinical decline from normal resting vitals to high-risk physiological decompensation over continuous ticks.
3. **`CRITICAL`**: Rapid physiological escalation (HR > 140, SBP < 65, RR > 35, Temp > 39.5 °C) designed to trigger existing Jeevan Setu Critical Universal Alerts.
4. **`RECOVERY`**: Starts in severe decompensation and gradually stabilizes back toward resting physiological parameters over 25–35 ticks.
5. **`MANUAL`**: Allows entering exact technical measurements with client and server-side range validation.

## 🚀 7. Operating Instructions

### A. Single Patient Simulation
1. Log in as an Administrator (`admin_js` / `Admin@123`).
2. Open `http://127.0.0.1:5000/Developer/Telemetry_Simulator/`.
3. Choose **Single** mode.
4. Select a patient from the database list.
5. Choose a Scenario (e.g. *Stable* or *Deterioration*).
6. Click **`START SIMULATION`**. Observe real-time vital telemetry tiles, server latency, and backend-calculated EWS.
7. Click **`STOP`** to pause transmission.
8. Click **`SEND ONE READING`** for isolated step testing.

### B. Concurrent Multi-Patient Simulation
1. Switch to **Multiple** mode (or click **`Select All`**).
2. Check multiple admitted patients from the list.
3. Configure individual scenarios in the matrix table (e.g., Patient 1 → Stable, Patient 2 → Critical).
4. Click **`START SELECTED PATIENTS`**.
5. All patients transmit concurrently with isolated asynchronous timers.
6. Click **`Stop`** on any row to pause an individual patient without interrupting others.
7. Click **`STOP ALL`** to halt all transmissions safely.

## 🔍 8. System Verification & Diagnostics

- **`Verify Database Data` (Read-Back Verification)**:
  Queries `GET /api/v1/vitals/patient/<id>/latest-status` and verifies that the database stored the exact values generated by the simulator.
- **`Verify EWS` (Relationship Integrity)**:
  Queries `GET /api/v1/vitals/<id>/latest` and confirms that `vitals.vital_id == ews.vital_id` and `ews.patient_id == patient_id`. Flags any relationship errors.
- **`Database Health Diagnostic`**:
  Measures round-trip MySQL query ping latency in milliseconds via `GET /api/v1/developer/telemetry-simulator/health` without exposing database credentials.
- **`Export Test Results`**:
  Downloads a complete session audit report in JSON containing latency statistics, success rates, and verification outcomes.

---

## 🛡️ 9. Concurrency & Safety Protections

- **Non-Overlapping Scheduling**: Each patient loop triggers its next request strictly *after* the preceding HTTP response resolves, preventing connection storms.
- **Zero Cross-Contamination**: Each patient maintains isolated scenario state, last readings, and metrics.
- **Auto-Backoff & Pause**: Repeated network errors (3 consecutive failures) pause simulation automatically with a notification.
- **Patient Change Safeguard**: Changing patient stops active transmission to prevent accidental data contamination.
- **Page Unload Cleanup**: All timers are cleanly terminated on `beforeunload` or logout.
